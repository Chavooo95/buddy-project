Comparativa técnica · ORMs en PHP
EloquentvsDoctrine
Diferencias, ventajas y desventajas de los dos ORMs dominantes de PHP — y por qué importa cuando construyes con DDD y Value Objects.
Contexto: basic_crud · Symfony + Doctrine (ORM/ODM) Patrón del proyecto: Data Mapper + Value Objects Fecha: 2026-07-29
La idea en una frase

La diferencia de fondo no es sintaxis: es Active Record frente a Data Mapper.

◆ Eloquent — Active Record
La entidad sabe cómo guardarse a sí misma.

El modelo extiende del ORM y mezcla datos + persistencia. $product->save(). Rapidísimo para CRUD; acoplado a la BD por diseño.

vs
◆ Doctrine — Data Mapper
La entidad no sabe nada de la BD.

Objetos PHP planos (POPO). Un EntityManager externo mapea y persiste. $em->persist($p); $em->flush();. Ideal para dominios ricos.

Todo lo demás (sintaxis, rendimiento, curva de aprendizaje, encaje con DDD) se deriva de esta única decisión de arquitectura.

¿Qué es cada uno?

ELOQUENT

El ORM que viene integrado en Laravel. Estándar de facto del ecosistema Laravel.

  • Patrón: Active Record
  • Filosofía: convención sobre configuración, "magia" productiva
  • Entidad = Modelo: extiende Model
  • Público objetivo: apps CRUD, MVP, startups, entregas rápidas
  • Desde: Laravel 4 (2013)
DOCTRINE

ORM independiente del framework. Estándar en Symfony; usable en cualquier proyecto PHP.

  • Patrón: Data Mapper + Unit of Work
  • Filosofía: explícito, desacoplado, dominio puro
  • Entidad = POPO: clase PHP sin herencia del ORM
  • Público objetivo: dominios complejos, DDD, sistemas de larga vida
  • Incluye: ORM (SQL) y ODM (MongoDB)

Definir una entidad / modelo

ELOQUENT 
class Product extends Model
{
    // tabla, PK, timestamps: por convención
    protected $fillable = ['name', 'price'];
}

// Uso
$p = Product::create(['name'=>'Book', 'price'=>9.99]);
$p->price = 12;
$p->save();
  • Cero configuración, casi cero código
  • Hereda ~50 métodos de persistencia
  • Modelo acoplado a la tabla y a la BD
DOCTRINE · tu Product real 
class Product   // POPO — sin extends
{
    public function __construct(
        private ProductId $id,
        private ProductName $name,
        private ProductPrice $price,
        private DateTimeInterface $createdAt,
    ) {}
    // mapeo en XML, fuera de la clase
}
  • Entidad de dominio pura — testeable sin BD
  • Constructor "siempre válido", invariantes garantizadas
  • Requiere definir el mapeo aparte

Persistencia

ELOQUENT · el modelo se guarda solo 
$p = Product::find(1);
$p->price = 20;
$p->save();      // UPDATE inmediato

Product::destroy(1);  // DELETE inmediato
  • Directo, intuitivo, una línea
  • Cada save() = un query (sin batching)
  • Sin seguimiento automático de cambios en lote
DOCTRINE · Unit of Work 
$p = $em->find(Product::class, $id);
$p->setPrice(new ProductPrice(20));

$em->flush();  // detecta cambios y
             // agrupa TODO en una transacción
  • Unit of Work: agrupa inserts/updates/deletes
  • Identity Map: una instancia por identidad
  • Dirty checking: no llamas a "save" por objeto
  • Hay que entender persist / flush / detach

Consultas

ELOQUENT · fluent query builder 
Product::where('name', 'like', "%$q%")
    ->orderBy('name')
    ->get();

$user->posts()->where(...)->get();
  • Legible, encadenable, muy rápido de escribir
  • Relaciones como métodos del modelo
  • Strings mágicos → errores en runtime, no compile
  • Fácil caer en N+1 sin darte cuenta
DOCTRINE · DQL / QueryBuilder · tu repo 
$em->createQueryBuilder()
   ->select('p')
   ->from(Product::class, 'p')
   ->andWhere('p.name LIKE :name')
   ->setParameter('name', "%$q%")
   ->getQuery()->getResult();
  • DQL razona en objetos, no en tablas
  • 100% portable entre motores SQL
  • Más verboso para consultas triviales
  • Encapsulado en repositorios (buen patrón DDD)

Value Objects & DDD — el corazón de tu proyecto

ELOQUENT · custom cast 
// Se apoya en "casts" del modelo
protected function casts(): array {
  return ['price' => PriceCast::class];
}
// PriceCast implements CastsAttributes
// get()/set() ↔ ProductPrice
  • Posible desde Laravel 7 (custom casts)
  • El VO vive "colgado" del modelo Active Record
  • El dominio sigue dependiendo del ORM
DOCTRINE · custom Type · ProductPriceType real 
final class ProductPriceType extends Type {
  public function convertToPHPValue($v,$p) {
    return new ProductPrice((float)$v);
  }
  public function convertToDatabaseValue($v,$p) {
    return $v->value;   // float en BD
  }
}
  • El VO es 100% del dominio, ignora la BD
  • Mapeo aislado en infraestructura
  • También Embeddables para VOs multi-campo

Eloquent — Ventajas & Desventajas

✔ Ventajas

  • Velocidad de desarrollo imbatible para CRUD
  • Curva de aprendizaje mínima; muy intuitivo
  • Convención sobre configuración → poco boilerplate
  • Ecosistema Laravel: scopes, eventos, factories, seeders
  • Relaciones expresivas y legibles
  • Documentación y comunidad enormes

✕ Desventajas

  • Acopla el dominio a la BD (mal encaje con DDD)
  • Tiende a modelos anémicos / "God models"
  • Difícil de testear sin base de datos
  • "Magia" implícita → sorpresas y N+1 ocultos
  • Sin Unit of Work ni Identity Map reales
  • Muy atado a Laravel (portabilidad baja)

Doctrine — Ventajas & Desventajas

✔ Ventajas

  • Dominio puro: entidades POPO, ideal para DDD
  • Unit of Work + Identity Map (transacciones y consistencia)
  • Value Objects / Embeddables de primera clase
  • Independiente del framework y del motor SQL
  • Testeabilidad alta (sin acoplar a la BD)
  • Escala a dominios grandes y de larga vida

✕ Desventajas

  • Curva de aprendizaje pronunciada
  • Más configuración y boilerplate (mapeo, types)
  • Overkill para CRUD sencillo / prototipos
  • persist/flush/detach confunden al principio
  • Puede consumir más memoria (tracking del UoW)
  • Menos "magia" → escribes más para lo simple

¿Cuándo usar cada uno?

Elige Eloquent si…

  • Ya trabajas en Laravel
  • La app es CRUD-céntrica (dashboards, back-offices)
  • Necesitas entregar rápido (MVP, startup)
  • El equipo es junior o valora la simplicidad
  • La lógica de negocio es ligera

Elige Doctrine si…

  • Aplicas DDD / arquitectura hexagonal
  • El dominio es complejo y de larga vida
  • Quieres el dominio desacoplado de la persistencia
  • Trabajas en Symfony o PHP puro
  • Necesitas transacciones y consistencia fuertes
No hay ganador absoluto: es un intercambio entre velocidad y simplicidad (Eloquent) frente a pureza del dominio y escalabilidad (Doctrine).
Conclusión · aplicado a basic_crud

Tu proyecto eligió Doctrine — y es coherente con lo que estás construyendo.

Por qué encaja aquí

  • Entidad Product POPO con constructor "siempre válido"
  • Value Objects (ProductId, ProductName, ProductPrice) con invariantes
  • Custom Types (ORM + ODM) que aíslan el mapeo
  • Repositorios tras una interfaz → dominio desacoplado

El precio que pagas

  • Más archivos: entidad, VOs, types, mapeo XML, repos
  • Hay que dominar persist / flush / Unit of Work
  • Para un CRUD "de libro", Eloquent sería más corto…
  • …pero perderías la pureza de dominio que buscas
Regla práctica: la complejidad del dominio manda. Dominio rico y duradero → Data Mapper (Doctrine). CRUD y velocidad → Active Record (Eloquent).
